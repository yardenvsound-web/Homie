## 3. התחברות והרשאות

### התחברות
- Supabase Auth, אימייל וסיסמה (`signInWithPassword`). שני חשבונות הורים נוצרים ידנית בדשבורד. אין הרשמה, שחזור סיסמה או כניסה עם Google.
- **הרשמה כבויה ב-Supabase (חובה).** ב-Authentication ← Sign In / Providers מכבים את "Allow new users to sign up". בלי זה, כל אדם יכול להירשם עם המפתח הציבורי שבדפדפן, להפוך ל-`authenticated` ולקרוא את כל הנתונים. היעדר מסך הרשמה באתר לא מספיק, כי אפשר לקרוא ל-`signUp` ישירות. את ההגדרה מבצע המשתמש בדשבורד.
- `supabase-js` שומר את ה-Session ואת רענון ה-Token אוטומטית, כך שהטאבלט נשאר מחובר (F02). הוא שומר אותו ב-localStorage כברירת מחדל. זה Token התחברות, לא נתוני המערכת.
- כל דף חוץ מ-`login.html` בודק Session בטעינה. אם אין, מפנה ל-`login.html`. זו נוחות בלבד. ההגנה האמיתית היא RLS.
- אחרי כניסה, `members.json` מזהה את ההורה לפי `supabase_user_id`, ורק כדי להציג את שמו.

### תפקידים
| תפקיד | חשבון | הרשאות |
|---|---|---|
| Parent / Admin (שניים) | יש, ב-Supabase Auth | כל מה שב-PRD. שני ההורים זהים. מזוהים ב-RLS לפי ה-uuid שלהם |
| פרופיל ילד | אין | נתון ב-`members.json` בלבד. הילד רואה את המערכת דרך Session של הורה |
| n8n | מפתח סודי של Supabase | כתיבה לטבלאות בעוקף RLS. נשמר רק ב-n8n |

### RLS
RLS מופעל על שלוש הטבלאות. אין Policy למשתמש אנונימי, כלומר חסימה מלאה.

**הגנה כפולה:** כל Policy מתירה גישה רק לשני ההורים, ולא לכל משתמש מחובר: התנאי הוא `auth.uid() in ('<uuid הורה 1>', '<uuid הורה 2>')`, עם אותם מזהים שב-`supabase_user_id` ב-`members.json`. כך, גם אם ההרשמה תיפתח בטעות, משתמש חדש לא יראה דבר. המזהים אינם סוד. **החלטה:** המזהים כתובים ישירות ב-`sql/policies.sql`, בלי טבלה נוספת.

| טבלה | שני ההורים (`auth.uid()` ברשימה) | כל משתמש אחר / anon |
|---|---|---|
| events | select, insert, update, delete (רק כש-`source = 'homie'`) | אין |
| tasks | select, insert, update, delete | אין |
| shopping_items | select, insert, update, delete | אין |

מחיקת משימה (F44) ומחיקת אירוע פנימי (F45) הן `delete` רגיל לפי `id`. ה-Policy של `delete` ב-`events` כוללת גם את התנאי `source = 'homie'`, כדי שאירוע Google לא יימחק (מחיקה שלו הייתה גורמת ל-W1 לקלוט אותו שוב). מחיקה מקבילה של אותו פריט על ידי שני ההורים לא דורשת עדכון מותנה: השנייה פשוט לא מוחקת דבר.

### עדכון מותנה
course-stack.md דורש עדכון מותנה כשפעולה יכולה להתבצע על ידי שני משתמשים בו-זמנית. לכן בפעולות אישור ודחייה:
- אישור אירוע Google: `update … where id = ? and status = 'pending'`.
- התעלמות מאירוע Google (F43): `update … set status = 'dismissed' where id = ? and status = 'pending'`.
- אישור או דחיית הצעת AI: `update … where id = ? and proposal_status = 'proposed'`.
- אם לא עודכנה אף שורה, הלקוח מציג "הפריט כבר טופל", ומרענן. עריכה רגילה של משימה או אירוע היא Last Write Wins ללא תנאי.

## 4. שכבת ה-AI

### עיקרון
המודל מציע בלבד. שום שינוי לא קורה בלי אישור הורה. הקריאה למודל לעולם לא יוצאת מהדפדפן.

### מודל וממשק
- מודל: `gemini-3.5-flash-lite` (ADR-14, 8.11.2026). במקור `gemini-3.8-flash`, כפי שאושר ב-tech-stack.md (14.10.2026). שם המודל מוגדר פעם אחת בהגדרות ה-Workflow (ואחרי MVP גם בפונקציה), כך שהחלפה היא שינוי במקום אחד.
- המכסה החינמית של המודל לא אומתה. בודקים אותה ב-AI Studio לפני ההרצה של `ai-tests.md`. אם היא נמוכה מדי, החלופה היא `gemini-3.5-flash-lite` (דורשת אישור).
- קריאה בנתיב ה-Interactions API: `POST https://generativelanguage.googleapis.com/v1beta/interactions`, המפתח בכותרת `x-goog-api-key`.
- פלט במבנה קבוע: `response_format` עם `type: text`, `mime_type: application/json` ו-`schema`.
- **החלטה:** לא ידוע לי שדה נפרד להוראות מערכת בממשק הזה, ולכן ההוראות והאירוע נשלחים יחד בשדה `input`.
- אם צומת Google Gemini ב-n8n לא תומך בפלט JSON קבוע, משתמשים בצומת HTTP Request עם אותו גוף.

### נתיב א' – אירוע Google (ב-MVP, F36 ו-F38)
**מי קורא:** n8n, ישירות. מפתח Gemini ב-Credentials של n8n.

**הפרומפט המרכזי** (מועתק מילה במילה מסעיף 10 ב-product-10-definitions.md; זה הנוסח הקובע, ואין לשנות אותו בלי אישור):

```
You are the AI suggestion layer of Homie, a family responsibility management system. You receive an approved or newly imported family event. Suggest one short, practical preparation task that could help the family get ready for the event. The suggestion must be directly related to the event context and should add useful information that is not already written in the event. Do not create, edit, assign or complete anything automatically. Return only a proposed task for parent approval. Do not invent personal facts about the family beyond the provided event data.
```

**מה נשלח למודל** (שדה `input`):
1. הפרומפט המרכזי שלמעלה, בלי שינוי.
2. פרטי האירוע בלבד כ-JSON: `title`, `date`, `start_time`, `end_time`, `notes`.
3. `notes` נחתך ל-500 תווים (course-stack.md: הגבלת אורך קלט).
4. לא נשלחים שמות בני בית, מזהים או כתובות מייל.
5. אחרי פרטי האירוע, שורה אחת: `Write the task title in Hebrew, up to 100 characters.` הפרומפט המרכזי עצמו לא משתנה (ADR-12, אושר 8.11.2026).

**סכמת הפלט:**
```json
{ "type": "object",
  "properties": { "title": { "type": "string" } },
  "required": ["title"] }
```

**בדיקה בקוד** (צומת Code ב-n8n, לפני שמירה): `title` הוא מחרוזת לא ריקה אחרי `trim`, באורך עד 100 תווים. אם הבדיקה נכשלת, או שהקריאה נכשלת, לא נשמרת הצעה, והאירוע נשמר כרגיל.

**מה נשמר** (שורה חדשה ב-`tasks`):

| שדה | ערך |
|---|---|
| title | `title` מהמודל |
| date | `date` של האירוע |
| time | null |
| status | `todo` |
| assigned_member_ids | `[]` |
| notes | `הצעה לאירוע: {כותרת האירוע}` |
| source | `ai` |
| proposal_status | `proposed` |

**זרימה אחרי הצעה:** ההצעה מופיעה ב-Pending. אישור מעדכן ל-`approved` והיא נעשית משימה רגילה שאפשר לערוך ולשייך (נשארת בלי שיוך עד שהורה משייך). דחייה מעדכנת ל-`rejected`.

### נתיב ב' – אירוע פנימי (אחרי MVP, F37)
**מי קורא:** פונקציה אחת, `api/suggest.js` ב-Vercel.

- הדפדפן שולח `POST /api/suggest` עם `Authorization: Bearer {access_token של ההורה}` וגוף עם פרטי האירוע (אותם שדות כמו בנתיב א').
- הפונקציה מאמתת את ה-Token מול Supabase Auth (`GET {SUPABASE_URL}/auth/v1/user` עם המפתח הציבורי). בלי Token תקין: `401`. **החלטה:** כך נקודת הקצה לא מאפשרת לכל אדם להשתמש במכסת המודל.
- היא מאשרת בקשות (CORS) רק מכתובת האתר ב-GitHub Pages, ועונה גם לבקשת OPTIONS.
- היא מגבילה את גוף הבקשה, קוראת למודל בנתיב ובסכמה זהים, ובודקת את הפלט.
- היא מחזירה תמיד JSON: `{ "ok": true, "title": "…" }` או `{ "ok": false, "error": "…" }`. בלי מפתח ובלי שגיאה גולמית של הספק.
- ה-JS בדפדפן שומר את ההצעה ב-`tasks` בשם המשתמש (RLS מתיר). **החלטה:** הפונקציה לא כותבת למסד, ולכן לא צריכה מפתח סודי של Supabase.
- משתני סביבה: `GEMINI_API_KEY`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`. אחרי שינוי משתנה – Redeploy.

### בדיקות

### Workflows ב-n8n

**W1 – Google → Pending ו-AI (ב-MVP: F31, F33, F36, F38)**
1. טריגרים: Schedule כל 4 שעות, ו-Manual Trigger להרצה לפני הדמו.
2. Google Calendar, Get Many events מהיומן, מהיום ועד 30 יום קדימה. **החלטה:** חלון של 30 יום, כדי להגביל את כמות האירועים.
3. לכל אירוע: חיפוש ב-`events` לפי `google_event_id`.
4. אם קיים, בכל סטטוס (כולל `dismissed`): דלג (עדכון הוא F32, אחרי MVP).
5. אם חדש: המרה ל-`date`, `start_time`, `end_time` בשעון ישראל, והכנסה ל-`events` עם `source = google`, `status = pending`, `assigned_member_ids = []`.
6. קריאה למודל לפי סעיף 4 נתיב א', בדיקה, והכנסת ההצעה ל-`tasks`.
7. אילוץ ה-unique על `google_event_id` הוא רשת ביטחון נגד כפילות.

**W2 – עדכון אירוע מ-Google (אחרי MVP, F32):** כמו W1, אבל לאירוע קיים: עדכון `title`, `date`, `start_time`, `end_time`, `notes` ו-`updated_from_google = true`. הסטטוס לא משתנה. הממשק מציג "עודכן ב-Google".

**מחיקה והחלפת הצעה (Milestone 9, F48, F49):** W1 קורא מ-Google גם אירועים שבוטלו. אירוע שבוטל ב-Google מסומן `dismissed`, והצעת ה-AI שלו שעדיין `proposed` נמחקת. כשאירוע משתנה (F32) ויש לו הצעה `proposed`, היא נמחקת והאירוע עובר שוב בקריאה למודל (סעיף 4, נתיב א'). הצעה שאושרה או נדחתה לא נוגעים בה. הפרטים הטכניים מתועדים ב-ADR בזמן הבנייה.

**W3 – מייל תזכורת למשימה (אחרי MVP, F34):** Schedule כל שעה. **החלטה:** שעה ולא 5 דקות, כדי להישאר במכסת ההרצות החודשית (tech-stack.md). שליפת משימות עם `reminder_at` שעבר, `reminder_sent = false` ו-`status = 'todo'`, שליחת מייל בצומת Gmail, ועדכון `reminder_sent = true`. הדיוק הוא שעה.

**W4 – מייל על אירוע Google חדש (אחרי MVP, Could, F35):** נקרא בסוף W1 אחרי הכנסה של אירוע חדש. שולח מייל לשני ההורים. כתובות המייל נשמרות בהגדרות ה-Workflow ב-n8n, לא בריפו.

### חזרתיות (F16, אחרי MVP) – בדפדפן
- בשמירת משימה עם `daily` או `weekly`, `js/recurrence.js` מחשב את המופעים: 28 שורות ליומית, 4 לשבועית (4 שבועות מיום התחלת המשימה). **החלטה:** שבועית חוזרת באותו יום בשבוע.
- הכנסה אחת (`insert` של מערך שורות). כל מופע שורה עצמאית.
- אין מחיקה או חידוש אוטומטי של מופעים. מחיקה ידנית (F44) מוחקת מופע אחד בלבד.

### חפיפות (F10, אחרי MVP) – בדפדפן
- `js/overlap.js` רץ על פריטי היום אחרי הטעינה, לכל בן בית בנפרד (לפי `assigned_member_ids`).

- הריפו ציבורי. אין בו מפתח סודי, לא בקוד, לא ב-HTML ולא בקבצי הגדרות, וגם לא ב-`n8n/*.json` (ייצוא Workflows ללא Credentials וללא כתובות מייל).

## 8. זרימות עיקריות – מהלך הנתונים

**טעינת לוח היום:** `auth.js` בודק Session ← `board.js` שולף tasks ו-events של היום הנבחר ← `members.js` מצמיד שם, צבע ו-Avatar ← רינדור ← `ui.js` מעדכן "עודכן לאחרונה".

**מעבר בין ימים (F42):** `board.js` מחזיק את היום הנבחר במשתנה בזיכרון בלבד (לא ב-localStorage ולא בכתובת), ומתחיל אותו בהיום לפי `time.js`. חץ מזיז אותו ביום אחד ושולף מחדש. "היום" מחזיר אותו להיום. רענון הדף חוזר להיום. **החלטה:** בלי פרמטר בכתובת, כדי להישאר פשוט.

**יצירת משימה:** כפתור + פותח `task-modal.js` ← בדיקת קלט (כותרת חובה, תאריך חובה) ← `tasks.insert` ← רענון הלוח. משימה חדשה: `status = todo`, `proposal_status = none`, `source = manual`.

**מחיקת משימה או אירוע פנימי:** "מחיקה" בחלון העריכה ← אישור קצר ← `tasks.delete` או `events.delete` לפי `id` ← סגירת החלון ורענון הלוח.

**שינוי סטטוס מכרטיס:** `tasks.update({status, updated_at}).eq('id', …)` ← רענון הכרטיס. עריכה מקבילה: Last Write Wins.

**אירוע Google, מקליטה ללוח:** W1 מכניס `pending` ← הורה נכנס ל-Pending (המונה מראה את הפריט) ← Modal אישור ושיוך ← עדכון מותנה (`status = pending`) ל-`approved` עם `assigned_member_ids` ← האירוע מופיע בלוח. או: "התעלם" בכרטיס ← עדכון מותנה ל-`dismissed` ← האירוע יוצא מהתיבה והמונה יורד.

**הצעת AI:** W1 שומר `proposed` ← הורה ב-Pending ← אישור (עדכון מותנה ל-`approved`) או דחייה (`rejected`) ← משימה מאושרת מופיעה בלוח.

**קניות:** Quick Add בודק (בלי רגישות לאותיות) אם קיים פריט פעיל באותו שם. אם כן, מתריע ומציע לעדכן כמות. אחרת `insert`. סימון "נקנה" מעדכן `purchased = true` והפריט נעלם. "בטל" בהודעה (F46, 5 שניות) מעדכן חזרה `purchased = false` ומרענן את הרשימה. מחיקה היא `delete` מיידי.

## החלטות מרכזיות (ADRs)

### ADR-1: הרצה מקומית בשרת סטטי של Python
**הקשר:** האתר בנוי ממודולי JS (`<script type="module">`) וטוען את `data/members.json` עם `fetch`. דפדפן חוסם את שניהם כשפותחים קובץ HTML ישירות מהמחשב (`file://`), ולכן צריך שרת מקומי כדי לבדוק את האתר לפני push. הסטאק אוסר כלי בנייה, ו-CLAUDE.md אוסר Docker.
**החלטה:** מריצים משורש הפרויקט את `python3 -m http.server 8000`, ופותחים `http://localhost:8000`. Python 3 כבר מותקן ב-Mac (נבדק: 3.9.6), ולכן אין צורך להתקין דבר. אם פורט 8000 תפוס, משתמשים בפורט אחר ומעדכנים את פקודת ההרצה ב-CLAUDE.md.
**השלכות:**
- אין קבצי הגדרה או תלויות חדשות בריפו. מה שרץ מקומית הוא בדיוק מה ש-GitHub Pages מגיש.
- כל הנתיבים בקוד יחסיים (`js/…`, `data/members.json`), כדי שיעבדו גם מקומית (`/`) וגם ב-GitHub Pages (`/Homie/`).
- הכניסה היא אימייל וסיסמה בלבד, ולכן Supabase לא צריך כתובת הפניה (Redirect URL) ל-localhost.
- האתר המקומי מתחבר לאותו פרויקט Supabase של האתר החי (אין הפרדה בין Development ל-Production ב-V1). נתוני הדמה משותפים לשניהם.

### ADR-2: תאריכי נתוני הדמה יחסיים להיום
**הקשר:** הלוח מציג את היום הנוכחי. נתוני דמה עם תאריכים קבועים היו משאירים את הלוח ריק בכל יום אחר שבו בודקים.
**החלטה:** `sql/seed.sql` מחשב כל תאריך כ-`(now() at time zone 'Asia/Jerusalem')::date + n`. הקובץ מוחק קודם את שלוש הטבלאות, ולכן אפשר להריץ אותו שוב בכל עת כדי לרענן את התאריכים.
**השלכות:** הרצה חוזרת של `seed.sql` מוחקת כל מה שנוצר באתר. זה מותר רק כל עוד יש במסד נתוני דמה בלבד.

### ADR-3: ניווט זמני עד Milestone 2
**הקשר:** ה-Definition of Done של Milestone 1 דורש מעבר בין הדפים, אבל סרגל הניווט (`js/nav.js`) נבנה רק ב-Milestone 2.
**החלטה:** `js/skeleton-nav.js` מוסיף לכל דף רשימת קישורים פשוטה (כולל "כניסה"), עם `aria-current` וקו תחתון לדף הנוכחי.

### ADR-8: חלונות עם `<dialog>` של הדפדפן
**הקשר:** DESIGN דורש בחלון (Modal) ש-Tab יישאר בתוכו, ש-Esc יסגור אותו, שלחיצה על שכבת ההכהיה לא תסגור, וש-Focus יחזור לכפתור שפתח. מימוש ידני של כל אלה הוא קוד רב, וספרייה אסורה בלי צורך.

**השלכות:** חלון האישור של Google (Milestone 6) ועריכת אירוע (Milestone 7) משתמשים באותם עזרים. אחרי מחיקה, ה-Focus עובר לכפתור ההוספה; אחרי עריכה, לכרטיס שנערך.

### ADR-9: אחרי שמירה הלוח עובר לתאריך הפריט

**החלטה:** אחרי שמירה, אם התאריך שונה מהיום המוצג, הלוח עובר לתאריך שנשמר (`afterSave` ב-`js/board.js`). אחרת הוא מתרענן במקום.

### ADR-10: הכנסת אירועי Google בבקשה אחת עם `ignore-duplicates`
**הקשר:** W1 (סעיף 5) מתאר חיפוש לפי `google_event_id` לכל אירוע, ואז הכנסה רק של החדשים. זה צומת חיפוש וצומת תנאי לכל אירוע, ושתי הרצות חופפות עלולות שתיהן להחליט שאירוע "חדש".
**החלטה:** n8n שולח את כל האירועים בבקשה אחת: `POST /rest/v1/events?on_conflict=google_event_id` עם `Prefer: resolution=ignore-duplicates,return=representation`. אילוץ ה-unique מדלג על כל אירוע שכבר קיים, בכל סטטוס (כולל `dismissed`), והתשובה מחזירה רק את השורות שנוספו עכשיו. רק הן ממשיכות לקריאה למודל.
**השלכות:** אותה התנהגות כמו בסעיף 5, עם פחות צמתים, ובטוח גם בהרצות חופפות. הרצה חוזרת לא יוצרת אירוע או הצעה כפולים. עדכון אירוע קיים (F32, אחרי MVP) יצטרך בקשה נפרדת, כי כאן אירוע קיים לא משתנה.

### ADR-11: מונה Pending נספר בכל טעינת דף

**השלכות:** המונה מדויק לרגע הטעינה או הרענון האחרון, כמו שאר הנתונים באתר.

### ADR-12: שורת שפה אחרי הפרומפט המרכזי

### ADR-13: קובצי Workflow מוכנים לייבוא
**הקשר:** המשתמש אינו מתכנת, ו-Claude לא נכנס ל-n8n.
**החלטה:** Claude כותב את `n8n/w1-google-to-pending.json` ו-`n8n/ai-tests.json` (בדיקות ה-AI בלי כתיבה למסד), והמשתמש מייבא אותם ובוחר את ה-Credentials בצמתים. שם המודל וכתובת Supabase מוגדרים פעם אחת בצומת **Settings**. הקבצים לא כוללים Credentials, כתובות מייל או מזהה יומן. אחרי הייבוא בוחרים בצומת Google Calendar את היומן מהרשימה (From list): יומן דמה נפרד בשם **Homie**, ולא היומן האישי, כי ל-Gemini בשכבה החינמית שולחים רק נתוני דמה. המילה `primary` לא מתקבלת בשדה By ID של n8n.
**השלכות:** אחרי שינוי ב-n8n מייצאים מחדש ומחליפים את הקובץ בריפו, ובודקים שאין בו סוד. ה-Credential של Supabase ב-n8n משתמש במפתח `service_role` הישן (Legacy), כי חיבור עם המפתח הסודי החדש (`sb_secret_…`) נכשל בבדיקה של n8n (8.11.2026). שניהם סודיים ונשמרים רק ב-n8n. הקריאה ל-Gemini כוללת את הכותרת `Api-Revision: 2026-05-20`, ‏`store: false` (לא שומרים את הבקשה אצל Google) ו-`thinking_level: low`, עם זמן המתנה של 90 שניות ובקשה אחת כל 12 שניות (מכסת השכבה החינמית). את ההצעה קוראים מהצעד האחרון מסוג `model_output` ב-`steps` של התשובה. ההרצה הראשונה, בלי אלה, נכשלה בזמן המתנה של 30 שניות (8.11.2026).

### ADR-15: "עדכון כמות" במוצר כפול מחליף את הכמות

### ADR-16: "עודכן לאחרונה" בכל דף שיש בו רענון
**הקשר:** DESIGN מציג את החיווי רק בלוח היום, אבל ARCHITECTURE (סעיף 5) קובע שהוא מוצג ליד כפתור הרענון, וכפתור הרענון קיים בשלושה דפים (ADR-7).
**החלטה (אושר על ידי המשתמש, 8.11.2026):** החיווי מוצג בלוח היום, בקניות ובממתין לאישור, תמיד ליד הרענון: בטלפון בתוך הדף, ובמחשב בסרגל העליון. `js/ui.js` שומר בזיכרון את שעת הטעינה המוצלחת האחרונה (`markLoading` / `markLoaded` / `markFailed`). בזמן טעינה מוצג "מעדכן…", ואחרי כישלון חוזרת השעה הקודמת ומופיעה גם בפס השגיאה. בלוח בטלפון, החיווי והרענון עוברים יחד לשורה שנייה כשכפתור "היום" מוצג. הודעת "בטל" בקניות (F46) עוצרת את ספירת 5 השניות כשהעכבר מעליה או כשה-Focus בתוכה, כדי שמשתמש מקלדת יספיק ללחוץ.
**השלכות:** השעה היא לכל דף בנפרד (בכל טעינת דף היא מתחילה מחדש), ואינה נשמרת ב-localStorage.

### ADR-17: כללי החפיפה, ומשימה שהושלמה לא נספרת
**הקשר:** F10 קובע שחפיפה בזמן אצל אותו בן בית מסומנת, וסעיף 5 מגדיר את הכלל. ה-spec לא אומר מה קורה למשימה שהושלמה, לפריט ללא שעה, או לשני טווחים שנוגעים זה בזה.
**החלטה (אושר על ידי המשתמש, 8.11.2026):** משימה בסטטוס `done` לא נספרת: לא גורמת לסימון ולא מקבלת אותו. `js/overlap.js` (חישוב בלבד, בלי DOM) בודק רק את פריטי היום המוצג שיש להם שעה ולפחות משויך אחד, ושני פריטים חופפים רק אם יש להם בן בית משותף. אירוע הוא `[start, end)`: אירוע שנגמר ב-11:00 ואירוע שמתחיל ב-11:00 לא חופפים, ומשימה ב-11:00 לא נופלת באירוע 10:00–11:00. אירוע בלי שעת סיום הוא נקודת זמן, ואירוע שעובר את חצות נמשך עד סוף היום (כמו ב-Timeline). הצ'יפ "חפיפה" נמצא בשורת סימונים מתחת לשעה ולמשויכים, ואחרי סימון Checkbox החפיפות מחושבות מחדש מהנתונים שבזיכרון, בלי טעינה ובלי ציור מחדש, כדי שה-Focus יישאר על ה-Checkbox.
**השלכות:** אין שמירה במסד ואין בקשה נוספת. אירוע של יום שלם לא מסומן אף פעם.

### ADR-18: עדכון מ-Google (F32) כענף ב-W1, לא W2 נפרד
**הקשר:** סעיף 5 מתאר את F32 כ-W2 "כמו W1". Workflow נפרד היה קורא שוב את Google Calendar ומכפיל את ההרצות במכסת n8n. ההכנסה ב-W1 (ADR-10) מדלגת על אירוע קיים ולכן לא יכולה לעדכן אותו.
**החלטה:** ב-`n8n/w1-google-to-pending.json` יוצא ענף שני מ-**Convert to Homie rows**: **Read existing Google events** (GET של אירועי Google שאינם `dismissed`), **Find changed events** (Code: השוואה לפי `google_event_id` של `title`, `date`, `start_time`, `end_time`, `notes`; שעות מנורמלות ל-`HH:mm`, הערה ריקה = `null`), ו-**Update changed events** (PATCH לכל אירוע שהשתנה, עם `updated_from_google = true` ו-`updated_at`). `status`, `assigned_member_ids` והצעת ה-AI לא משתנים. אירוע `dismissed` לא מתעדכן.
**השלכות:** רק שינוי אמיתי מסמן "עודכן ב-Google", והרצה חוזרת בלי שינוי לא כותבת כלום. הסימון נשאר אחרי שהופיע (ה-spec לא מגדיר כיבוי). אירוע שנמחק ב-Google, או שזז מעבר ל-30 הימים, לא משתקף ב-Homie. הצ'יפ מוצג בכרטיס אירוע Google בלוח ובממתין לאישור. שלושת הצמתים נוספו ל-W1 ב-n8n ישירות דרך החיבור של Claude ל-n8n (8.11.2026), עם ה-Credential הקיים של Supabase, והקובץ בריפו כולל אותם. נבדק מקצה לקצה: שינוי שעה של אירוע ממתין ושינוי שם של אירוע מאושר התעדכנו במקום, והרצה חוזרת לא כתבה דבר.

### ADR-19: מחיקה מ-Google והחלפת הצעה ממתינה בשרשרת אחת ב-W1 (F48, F49)
**הקשר:** F48 ו-F49 דורשים ש-W1 יזהה אירועים שנמחקו ב-Google, וימחק או יחליף את הצעת ה-AI הממתינה של אירוע שנמחק או השתנה. אין בטבלה עמודה שמקשרת הצעה לאירוע, ואין שינוי במבנה מסד הנתונים. ב-ADR-18 הענף של העדכון רץ במקביל להכנסה, ו-**Convert to Homie rows** עצר את כל השרשרת כשלא היו אירועים.
**החלטה:**
- **זיהוי מחיקה:** צומת Google Calendar עם `showDeleted`. אירוע עם `status = 'cancelled'` נכנס ל-`cancelled_ids`. מחיקה מזוהה **רק** לפי הסימון המפורש הזה, ולא לפי אירוע שחסר ברשימה, כדי שתקלה בקריאה לא תעלים אירועים. אירוע שבוטל ונמצא במסד (לא `dismissed`) מקבל `status = 'dismissed'`.
- **קישור הצעה לאירוע:** לפי `source = 'ai'`, `proposal_status = 'proposed'`, `notes = "הצעה לאירוע: <שם>"` ו-`date`, לפי הנתונים **הישנים** של האירוע במסד (לפני העדכון).
- **השרשרת לינארית ותמיד ממשיכה:** Convert (מחזיר תמיד פריט אחד `{ rows, cancelled_ids }`) ← Read existing Google events ← Read pending suggestions ← **Find changes** (פריט אחד: `updates`, `dismiss_ids`, `stale_suggestion_ids`, `events_for_ai`) ← Dismiss deleted events (PATCH אחד) ← Delete stale suggestions (DELETE אחד, רק `proposed`) ← Insert new events ← **Events for AI** (אירועים חדשים + אירועים שהשתנו והייתה להם הצעה ממתינה) ← אותה שרשרת AI. העדכונים (F32) עוברים בענף צדדי: Split updates ← Update changed events. בבקשה עם רשימה ריקה נשלח מזהה ממלא מקום (`00000000-…`) שלא מתאים לאף שורה, וצמתי ה-HTTP מוגדרים Always Output Data ו-Execute Once, כך שאף צעד לא עוצר את השרשרת.
- אירוע שהשתנה בלי הצעה ממתינה (אין, או שאושרה או נדחתה) לא נשלח למודל. כשהקריאה למודל נכשלת, האירוע כבר עודכן וההצעה הישנה כבר נמחקה, ואין הצעה.
- **F50 בדפדפן:** `isRecentGoogleUpdate` ב-`js/ui.js`: הצ'יפ מוצג אם `updated_from_google` וגם `updated_at` לפני פחות מ-72 שעות. `updated_at` נשלף בלוח ובממתין לאישור.
**השלכות:**
- שני אירועים עם אותו שם ואותו תאריך לא מובחנים: שינוי באחד מוחק גם את ההצעה הממתינה של השני (נדיר).
- אירוע שהועבר ב-Google לתאריך מעבר ל-30 הימים לא מסומן `cancelled`, ולכן נשאר בלוח עם הפרטים הישנים. אירוע שנמחק אחרי שתאריכו עבר לא נבדק.
- אירוע שנמחק ושוחזר ב-Google לא חוזר (כבר `dismissed`, כמו אחרי "התעלם").
- גם אישור אירוע ממתין מעדכן את `updated_at`, ולכן אירוע שעודכן ב-Google ואושר אחר כך מציג את הצ'יפ 3 ימים מהאישור.
- מחליף את ההשלכות של ADR-18 לגבי מחיקה ולגבי הסימון שנשאר לתמיד.
- נבדק מקצה לקצה ביומן הבדיקה Homie (8.11.2026): אירוע ממתין ואירוע מאושר שנמחקו סומנו `dismissed`, ההצעה הממתינה נמחקה, ומשימה שאושרה נשארה. שינוי שם ושעה החליף הצעה ממתינה בהצעה אחת חדשה, והצעה שאושרה או נדחתה לא השתנתה. כישלון מודל (שם מודל שגוי זמנית): האירוע עודכן ולא נשארה הצעה. הרצה חוזרת בלי שינוי לא שינתה דבר במסד.
