## 5. שכבת הנתונים (`js/data/*.js`)

**`events.js`**
- `getPendingEvents()` – `status = 'pending'`, השדות `id, title, date, start_time, end_time, notes`, ממוין לפי `date` ואז `start_time` (יום שלם קודם). כולל אירועים שתאריכם עבר (PRD 4.14: נשארים עד טיפול).
- `countPendingEvents()` – `select('id', { count: 'exact', head: true })` עם אותו תנאי.
- `approveGoogleEvent(id, memberIds)` – **עדכון מותנה** (ARCHITECTURE סעיף 3): `update({ status: 'approved', assigned_member_ids, updated_at }).eq('id', id).eq('status', 'pending').select('id')` ← `{ found }`.
- `dismissGoogleEvent(id)` – אותו דבר עם `status: 'dismissed'`.

**`tasks.js`**
- `getProposedTasks()` – `proposal_status = 'proposed'`, השדות `id, title, date, notes`, ממוין לפי `date` ואז `created_at`.
- `countProposedTasks()` – כמו למעלה, `head: true`.
- `approveSuggestion(id)` / `rejectSuggestion(id)` – `update({ proposal_status: 'approved' | 'rejected', updated_at }).eq('id', id).eq('proposal_status', 'proposed').select('id')` ← `{ found }`. משימה מאושרת נשארת `source = 'ai'`, בלי שיוך, ו-`getBoardTasks` כבר מציג `approved`.

`found: false` = ההורה השני כבר טיפל בפריט: הדף מציג "הפריט כבר טופל" ומרענן.

## 6. מונה Pending בסרגל (`js/nav.js`)

- אחרי `renderNav`, ‏`initProtectedPage` שולף `countPendingEvents() + countProposedTasks()` (שתי בקשות במקביל) ומציג את הסכום בלשונית "ממתין לאישור", בסרגל העליון ובתחתון.
- המונה: עיגול אדום (`--color-danger`, טקסט לבן) עם המספר. כשהסכום 0 – מוסתר. המספר עצמו הוא החיווי, לא הצבע.
- נגישות: הקישור מקבל `aria-label` "ממתין לאישור, 3 פריטים"; העיגול עצמו `aria-hidden`.
- אם הספירה נכשלת – אין מונה, בלי הודעת שגיאה (הדף עצמו ממשיך לעבוד). בדף Pending הספירה מגיעה מהנתונים שנטענו, בלי בקשה נוספת.
- `setPendingCount(n)` מיוצא, כדי שדף Pending יעדכן את המונה (בסרגל ובכותרת) אחרי כל פעולה ואחרי רענון.
- גם רענון בלוח היום ובקניות מעדכן את המונה (קריאה ל-`refreshPendingCount()` מתוך `onRefresh`).

- אזור התראות (פס שגיאה), שלד טעינה.
- קטע **"אירועי Google חדשים"** (`h2` + רשימה). כרטיס: שם האירוע, שורת "יום ב׳ · 13.10 · 17:00–18:30" (או "יום שלם") עם אייקון שעון, תג המקור "Google", כפתור ראשי "בדוק ואשר" ואחריו משני "התעלם".

- קטע ריק מוסתר. כששני הקטעים ריקים: כרטיס ריק קומפקטי "אין פריטים שממתינים" (DESIGN, "מצבים").
- כל טקסט שמגיע מ-Google או מהמודל – `textContent` בלבד (ARCHITECTURE סעיף 6).

**התנהגות:**
- טעינה: `getPendingEvents()` ו-`getProposedTasks()` במקביל, עם `loadSeq` נגד תשובות ישנות (כמו בקניות). שגיאה ← פס "לא הצלחנו לעדכן" + "נסו שוב".
- **"בדוק ואשר"** ← `openGoogleApproveModal`. אחרי אישור: הכרטיס יוצא, המונה יורד, והפוקוס עובר לכרטיס הבא (או לכותרת הקטע / לכותרת הדף).
- **"התעלם"** ← בלי חלון אישור (DESIGN): הכפתורים בכרטיס ננעלים, `dismissGoogleEvent`, הכרטיס יוצא והמונה יורד. בכישלון: הכרטיס נשאר והודעת "לא הצלחנו לשמור את השינוי".
- **"אשר" / "דחה"** בהצעה – אותו דפוס, עם `approveSuggestion` / `rejectSuggestion`.
- `found: false` בכל פעולה ← הודעה "הפריט כבר טופל" וטעינה מחדש של הדף.
- הצעת AI של אירוע שההורה התעלם ממנו נשארת בתיבה, וההורה דוחה אותה בנפרד (PRD 4.14). אין קישור בין השתיים.
- רענון: `onRefresh` ל-`initProtectedPage` (כפתור במחשב) + כפתור בטלפון.

## 9. Workflow W1 ב-n8n (`n8n/w1-google-to-pending.json`)

Claude כותב את הקובץ, אתה מייבא (Workflows ← Import from File) ובוחר את ה-Credentials בכל צומת. הצמתים:

1. **Schedule Trigger** – כל 4 שעות. **Manual Trigger** – להרצה ידנית (F33). שניהם מחוברים לצומת הבא.
2. **Google Calendar – Get Many** – יומן `primary`, מהיום ועד 30 יום קדימה, Single Events = כן (מופעים של אירוע חוזר כאירועים נפרדים, לכל אחד `id` משלו), Return All.
3. **Code – המרה** (JS, עם Luxon שמובנה ב-n8n):
   - מדלג על אירוע `status = 'cancelled'`.
   - `start.dateTime` ← `date` ו-`start_time` בשעון ישראל (`setZone('Asia/Jerusalem')`); `end.dateTime` ← `end_time`.
   - `start.date` (יום שלם) ← `date`, ושתי השעות `null`. אירוע של כמה ימים – ביום ההתחלה בלבד (ARCHITECTURE סעיף 2).
   - `title` = `summary` (ריק ← "אירוע ללא שם"), חתוך ל-100 תווים. `notes` = `description` חתוך ל-500 תווים, או `null`.
   - שדות קבועים: `source: 'google'`, `status: 'pending'`, `assigned_member_ids: []`, `google_event_id: id`.
4. **HTTP Request – הכנסה ל-`events` בלי כפילויות** (Credential של Supabase):
   `POST {SUPABASE_URL}/rest/v1/events?on_conflict=google_event_id` עם הכותרת `Prefer: resolution=ignore-duplicates,return=representation`, וכל האירועים בבקשה אחת.
   התשובה מחזירה **רק את השורות שנוספו עכשיו**. אירוע שכבר קיים – בכל סטטוס, כולל `dismissed` – לא נוגעים בו ולא חוזר (DoD: הרצה שנייה, "התעלם").
   *זו דרך פשוטה יותר לשלבים 3–5 ב-W1 (ARCHITECTURE סעיף 5): במקום חיפוש לכל אירוע ואז הכנסה, הכנסה אחת שמסתמכת על אילוץ ה-unique. התוצאה זהה, עם פחות צמתים, וגם בטוח כששתי הרצות חופפות. מתועד כ-ADR.*
5. **לכל אירוע חדש – Code: בניית הבקשה למודל**: הפרומפט המרכזי **מילה במילה** (ARCHITECTURE סעיף 4), ואחריו JSON של `title, date, start_time, end_time, notes` (notes עד 500 תווים). בלי שמות בני בית, מזהים או מיילים. ואחריהם שורת השפה (סעיף 0).
6. **HTTP Request – Gemini** (Credential של Gemini): `POST https://generativelanguage.googleapis.com/v1beta/interactions`, המודל `gemini-3.8-flash` מוגדר במקום אחד (צומת Set בתחילת ה-Workflow), `response_format` עם `mime_type: application/json` והסכמה `{ title: string }`. **On Error: Continue** – כישלון לא עוצר את ה-Workflow.
7. **Code – בדיקה**: מוציא את `title` מהתשובה, בודק שזו מחרוזת לא ריקה אחרי `trim` ועד 100 תווים. אחרת (או כשהקריאה נכשלה) – הפריט נזרק, ולא נשמרת הצעה. האירוע כבר נשמר בשלב 4 (DoD: "כשהקריאה למודל נכשלת, האירוע עדיין נקלט").
8. **HTTP Request – הכנסה ל-`tasks`**: `title` מהמודל, `date` של האירוע, `time: null`, `status: 'todo'`, `assigned_member_ids: []`, `notes: 'הצעה לאירוע: {כותרת}'`, `source: 'ai'`, `proposal_status: 'proposed'`.

כיוון שרק אירועים חדשים מגיעים לשלב 5, הרצה חוזרת לא יוצרת הצעה כפולה.

**נקודות לבדוק בזמן הבנייה (לא אומתו בתיעוד):**
- שמבנה הבקשה והתשובה של ה-Interactions API (`input`, `response_format`, איפה הטקסט בתשובה) תואם את מה שכתוב בקובץ. אם לא – מתקנים לפי התיעוד העדכני.
- שהמפתח הסודי החדש של Supabase (`sb_secret_…`) עובד עם ה-Credential של Supabase ב-n8n בבקשת HTTP. אם לא – משתמשים במפתח `service_role` הישן (Legacy), שגם הוא סודי ונשמר רק ב-n8n.
- שהיומן בחשבון Google מוגדר לשעון ישראל (ההמרה בקוד ממילא לא תלויה בזה).

**ייצוא לריפו:** אחרי שהכול עובד, מייצאים את ה-Workflow מ-n8n ומחליפים את הקובץ. Claude בודק שאין בו מפתח, טוקן, כתובת מייל או מזהה יומן אישי (n8n מייצא רק את שם ה-Credential, לא את הסוד).

**תדירות:** כל 4 שעות ≈ 180 הרצות בחודש, בתוך מכסת הניסיון (tech-stack.md). אפשר להשאיר את ה-Schedule כבוי עד קרוב להצגה ולהריץ ידנית.
